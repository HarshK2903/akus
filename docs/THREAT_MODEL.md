# Foundation security boundary

Implemented: opt-in loopback-only demo origin, fail-closed production mode, server-resolved fixture identity, forbidden input extras, opaque random session cookies, SHA-256 session hashes, expiry/rotation/logout, exact Origin and CSRF validation on source mutations and logout, authenticated/scoped reads, safe database/validation errors and correlation IDs, append-only audit triggers. Web contains no privileged academic actions. Caddy config includes CSP, nosniff and frame restrictions.

The local fixture selector intentionally allows anyone with access to this local demo to select fictional identities. This is not institutional authentication. Native PostgreSQL uses trust on loopback for fictional data; Compose uses explicit demo credentials without publishing the DB port. Never expose either demo to public traffic or real records.

Phase 2 must implement Google state/nonce/signature/audience/issuer/expiry checks, roster linking, Secure cookies, anti-CSRF bootstrap, institutional session provisioning and revocation. Effective employment/office revalidation and global DRC/HoD exclusivity now exist in Phase 2A with explicit fictional source records. Domain slices must enforce ownership, department scope, no self-review, current authority, race-safe quotas and idempotency. Other pending hardening: auth throttling, runtime least-privilege database roles, upload scanning/private storage, source SSRF/sanitization, export controls, retention policy, TLS, backups/restore and intrusion monitoring. No production readiness claim.

Phase 2A commands require a separate current Admin grant, lock/recheck authority, validate idempotency keys and audit atomically. Principal source reads are global but its role does not grant writes. DRC/Faculty can read self; HoD reads current scope. API tests cover cross-department IDOR, stale/expired authority, fixture-label forgery, missing CSRF and competing commands. Google issuer/subject linking and real institutional sessions remain unimplemented.
